Roadmap موبایل — Podman Ban

نقشهٔ کار برای اینکه پروژهٔ فعلی روی گوشی «استاندارد و حرفه‌ای» شود، بدون تغییر کد.

توضیحات به زبان ساده نوشته شده‌اند تا کسی که برنامه‌نویس نیست هم بفهمد.

۱. مقایسهٔ YPT و پروژهٔ ما

YPT یک اپلیکیشن تایمر مطالعه است. کاربر تایمر را روشن می‌کند و تا داخل اپ بماند زمان جمع می‌شود؛ نوتیف ساده دارد و بیشتر روی «تجربهٔ موبایل» تمرکز دارد.

پروژهٔ ما قابلیت‌های بیشتر دارد (اتاق مطالعه، آزمون، رتبه‌بندی، اعلان ادمین)، ولی باید روی **رفتار موبایل** (پس‌زمینه، نوتیف، دکمهٔ برگشت، صفحه‌کلید) بهتر شود.

۲. ایرادات با مثال ساده (قبل/بعد از رفع)

۲.۱ دکمهٔ «برگشت» روی گوشی

کاربر در امتحان است. انگشت تصادفی swipe/back می‌کند.
قبل از رفع
امتحان ممکن است بسته شود یا وضعیت گم شود. مثل «پروندهٔ نیم‌کاره» بدون پرسش saves.
بعد از رفع
گوشی می‌پرسد: «آیا می‌خواهید آزمون را ببندید؟» با انتخاب «خیر»، جلوگیری می‌شود. پیشرفت کاربر محفوظ می‌ماند.

۲.۲ یادآوری ساعت ۲۳:۰۰

کاربر هر روز سوال پاسخ می‌دهد. app بسته است.
قبل از رفع
پیام ۲۳:۰۰ نمی‌آید، چون تایمر داخل JavaScript فقط وقتی app باز است کار می‌کند.
بعد از رفع
گوشی خودش one scheduled reminder دارد (مثل alarm app). حتی اگر پروژهٔ ما app بسته باشد، پیام_reminder می‌آید.

۲.۳ نوتیف تایمر freeze می‌شود

کاربر تایمر را روشن می‌کند و ۴۰ دقیقه app بسته است.
قبل از رفع
notification شاید بگوید «۲۵ دقیقه» ولی time واقعی است ۶۵ دقیقه. وقتی reopen, timer «jump» می‌کند.
بعد از رفع
notification هر دقیقه به‌روز می‌شود (مثل stopwatch system). روی return هم همان زمان را نشان می‌دهد.

۲.۴ تشخیص «موبایل واقعی» ضعیف است

کاربر نسخهٔ APK روی گوشی Samsung نصب می‌کند، ولی بعضی قابلیت‌ها کار نمی‌کنند.
قبل از رفع
app گاهی نمی‌فهمد که روی Android است → نوتیف‌ها ساخته نمی‌شوند / یادگیری‌شتن permission رو ظاهر نمی‌شود / uploadها corrupted می‌شوند.
بعد از رفع
تشخیص قابل‌اعتماد → همهٔ قابلیت‌های موبایل روی همهٔ گوشی‌ها فعال می‌شوند.

۲.۵ پاسخ‌های آزمون در شبکهٔ ضعیف از بین می‌روند

کاربر در subway مترو ۲۰ سوال tap می‌کند؛ سپس app killed می‌شود.
قبل از رفع
پاسخ‌های نیمه‌ارسال in-memoryند → از بین می‌روند → نمرهٔ نهایی با UI ممکن است mismatch بسازد.
بعد از رفع
پاسخ‌ها در یک queue ذخیره شده (draft) و پس از reconnect retry می‌شوند. نمره با چیزی که کاربر دید هم‌راستا می‌ماند.

۲.۶ مصرف باتری و دادهٔ زیاد

300 user همزمان app باز دارند → ثانیه‌ای همیشه server check.
قبل از رفع
ترافیک عظیم → سرور کندتر → network error بیشتر → کارفر باتری drain می‌کند.
بعد از رفع
گوشی only when needed/preferences سرور를 check می‌کند یا WebSocket updates → smoother و کمتر charging.

۲.۷ صفحه‌کلید forms را می‌پوشاند

کاربر روی گوشی کوچک login می‌کند.
قبل از رفع
input پشت keyboard می‌ماند، دکمهٔ submit نمایان نیست → mis-tap.
بعد از رفع
فرم auto scroll/resize می‌کند → همه inputs و buttons قابل دسترسی.

۳. Roadmap ساده (مثل یک به‌روزرسانی مرحله‌ای)

Phase 0 — بررسی (Audit)

مثل «چک آپ» قبل از تعمیر: همهٔ گوشی‌ها/شبکه‌ها را test می‌کنیم تا ببینیم قبل/بعد چه تفاوتی دارد.

Phase 1 — کارهای حیاتی (P0)

۱) back button fix، ۲) timer notification real-time، ۳) reminder alarm native، ۴) permission deep-link.

نتیجه: کمتر accidental loss و بهتر reliability.

Phase 2 — ذخیرهٔ قوی + Offline (P1)

پاسخ‌ها ذخیره شده، offline overview cache، polling adaptive.

نتیجه: subway/bus robust.

Phase 3 — polish Native (P2)

haptics, keyboard plugin, notification deep link, widgets, adaptive icons.

Phase 4 — Store readiness

AAB signing, permissions docs, crash analytics, pre-launch testing.

۴. مثال «قبل/بعد» در یک جمله (خیلی ساده)

  • Exit confirm: قبل: swipe تصادفی exam می‌بندد. بعد: «آیا ببندم؟».
  • Reminder: قبل: ۲۳:۰۰ هرگز نمی‌آید. بعد: هر روز می‌آید.
  • Timer notification: قبل: زمان frozen. بعد: زمان live.
  • Weak network answers: قبل: پاسخ lost. بعد: resend safe.
  • Battery: قبل: app همیشه poll. بعد: only needed.
  • Keyboard: قبل: input پشت keyboard. بعد: auto-scroll.

۶. بقیهٔ ایرادات (پنهان ولی مهم)

اینها را هم در بررسی‌ها دیدیم. بعضی‌ها کوچک ولی روی گوشی‌ها اذیت‌کننده می‌شوند.

Service Worker دیر ثبت می‌شود

ثبت SW تا پس از بارگذاری کامل صفحه صبر می‌کند؛ در صورت کندی، قابلیت «app مثل app» شدن دیر فعال می‌شود. sw-register.tsx

PWA install prompt ندارد

هیچ «Add to Home Screen» button/helper در UI دیده نشد. کاربران گوشی web-to-app install flow دستی دارند. manifest.webmanifest + sw-register

Deep navigation recovery در offline شکننده است

Service Worker فقط صفحهٔ اصلی («/») را برای fallback کش می‌کند. اگر کاربر در nested route (مثلاً study detail) offline شود و reload کند، به صفحهٔ اصلی برمی‌گردد. sw.js

OAuth cold-start برگشت ممکن است drop شود

listener فقط `appUrlOpen` را گوش می‌دهد. اگر app کاملاً kill شده و via deep link باز شود، ticket در callback ممکن است نادیده گرفته شود. social-buttons.tsx

Theme-color ثابت و light-only

`theme-color` = #FAFAFA است ولی dark mode ندارد. روی موبایل، status bar/header در dark بی‌هماهنگی به نظر می‌رسد. index.html

Portrait lock ممکن است UX tablet ها را محدود کند

Manifest `orientation: portrait-primary`. روی tablet/landscape user، app rotate نمی‌شود. manifest.webmanifest

ادمین broadcast بدون push

تنها poll every 60s. اگر app fully closed باشد، broadcast تا open خوانده نمی‌شود. notify-inbox.ts

Pollingهای چندگانه باتری را مصرف می‌کنند

online status هر 30s probe می‌کند + study rooms every 10s + config/broadcast 60s. روی 3G battery/data ضربه می‌زند. use-online-status.ts, study-view.tsx

Permission denied بدون Settings deep-link

اگر user “Don’t allow” انتخاب کند، هیچ راه guided برای re-enable وجود ندارد. background-permission.tsx

Duplicate source-of-truth for native flags

`isNativeApp()` دوبار duplicate شده؛ behavior drift risk بین api-client و native-notify. api-client.ts + native-notify.ts

Auth refresh edge cases trên mobile network

doRefresh + socket reconnect loops روی weak network ممکن است repeated retries ایجاد کند. api-client.ts + chat socket

Account deletion / Data safety not evident

هیچ auth endpoint/UI clear “delete my account” دیده نشد. برای Play Store data safety الزامات دارد. auth routes/store

Anti-tamper signature guard can break updates

زمانی که keystore/signing path تغییر کند، app die می‌شود تا fingerprint match شود. برای standard release workflow risk است. build-apk.yml injects MainActivity

Base64 upload memory overhead

فایلٔ بزرگ در base64 (در RAM) برای phoneٔ کم مموری heavy است. api-client.ts upload

No native crash analytics end-to-end visible

client error reporting exists، ولی تأیید نشد که mobile crashes را با contextual session/timer data capture کند. error-report.ts

۷. Checklist اولویت‌دار (Phase 0/1/2/3/4)

این چک‌لیست برای دنبال کردن پیشرفت بدون بار کردن خاطر کاربر نهایی طراحی شده است. خودِ تیم فنی موارد را tick کند.

Phase 0 — Audit (بدون تغییر کد)

  • ☐ روی 3 گوشی مختلف (Samsung / Xiaomi / Pixel) on-device audit `isNativeApp`
  • ☐ جدول قبل/بعد نوتیف تایمر بساز (freeze issue)
  • ☐ جدول battery probe 24h baseline
  • ☐ سنجیدن permission flow (allow/deny/settings)
  • ☐ سنجیدن offline fallback deep routes
  • ☐ capture crash baseline + load p95

Phase 1 — Reliability هسته (P0)

  • ☐ Back button handler + exam exit confirm consumption
  • ☐ Study timer Foreground Service + notification channels
  • ☐ Daily reminder native alarm / FCM scheduled
  • ☐ Permission denied → settings deep-link
  • ☐ normalized native detection (one source) + safety audit

Phase 2 — Durable Data & Offline (P1)

  • ☐ durable sync queue (answers, study act events)
  • ☐ offline cache for overview/leaderboard snapshots
  • ☐ visibility-gated polling + adaptive intervals
  • ☐ online status probe consolidation (one interval)
  • ☐ OAuth cold-start deep-link ticket handler

Phase 3 — Native Polish (P2)

  • ☐ keyboard plugin + resize policy
  • ☐ haptics on timer thresholds
  • ☐ notification deep-link to exact view
  • ☐ widgets daily goal
  • ☐ adaptive icons raster + splash

Phase 4 — Store readiness & Observability

  • ☐ AAB + Play App Signing + targetSdk review
  • ☐ permission/data safety docs + privacy/account deletion
  • ☐ crash analytics end-to-end verified
  • ☐ pre-launch test matrix (Android 12-15)
  • ☐ performance profiling low-end devices
